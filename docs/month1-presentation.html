The gap: almost everything published is a desktop plugin that assumes a person sitting in front of QGIS. A headless, HTTP-accessible bridge is a largely unoccupied position — and it is what you need to put spatial analysis behind a web app, a scheduled job, or a larger agent.

Week 1 · Evidence

Someone already measured the choice I had to make

GeoJSON Agents (Luo et al., 2025) built the same geospatial system twice — once generating code, once calling predefined functions — and scored both.

97.1%Code generation
85.7%Function calling — our approach
48.6%Unaided model

Read honestly: code generation scored higher. It is more flexible on open-ended tasks. Function calling wins on execution stability — and it can be validated before anything runs.

For a system running unattended on a server, touching real files, I chose the option that fails safely and explains itself. Both structured approaches roughly doubled an unaided model, which is the argument for building any structured layer at all.

Weeks 2–3 · Foundations

QGIS with no interface, behind a web service

Week 2 — Headless

An LLM cannot click buttons, so QGIS had to run without a window. Python 3.12 + QGIS 3.44.11 via conda-forge, driven through PyQGIS.

The hard part was environmental: QGIS's own conda activation hook is broken on Windows — it assumes a Linux directory layout and joins paths with : where Windows needs ; — so import qgis failed silently. Diagnosed and fixed in fix_qgis_env.sh.

Week 3 — The bridge

A FastAPI server that boots QGIS once and keeps it alive, so loading 440 algorithms is paid for a single time rather than on every request.

Interactive documentation generates itself at /docs. Endpoints: /health, /algorithms, /run — plus the Week 4 additions /tools and /tools/execute.

Both layers are shared code, not duplicates: the headless startup lives in one module, qgis_engine.py, used by the test script and the server alike.

Week 4 · The deliverable

The model fills in a form. It never writes code.

Each tool is one Python class that generates both the schema sent to the model and the validation applied to what comes back — so the advertised contract and the enforced contract cannot drift apart.

{
  "name": "buffer_layer",
  "description": "Draw a zone of a given distance in metres around every
                  feature in a layer. The distance is always in METRES —
                  this tool handles the coordinate-system conversion itself.",
  "input_schema": {
    "type": "object",
    "properties": {
      "layer":           { "type": "string",  "description": "The layer to buffer" },
      "distance_meters": { "type": "number",  "description": "Buffer distance in metres" },
      "dissolve":        { "anyOf": [{"type": "boolean"}, {"type": "null"}] },
      "output_name":     { "anyOf": [{"type": "string"},  {"type": "null"}] }
    },
    "required": ["layer", "distance_meters", "dissolve", "output_name"],
    "additionalProperties": false   // it cannot invent arguments
  },
  "strict": true
}

11 tools in two groups — inspection (list_available_layers, describe_layer) so the agent can look before it leaps, and geoprocessing (buffer, clip, intersect, dissolve, filter, spatial join, centroids, convex hull, reproject).

Week 4 · Why it matters

Every bad request is refused — in words the model can act on

The model does thisIt gets back
Calls a tool that doesn't exist There is no tool called 'delete_everything'. Available tools: …
Sends "distance_meters": "quite far" Input should be a valid number…
Invents an extra argument 'colour': Extra inputs are not permitted
Asks for C:/Windows/win.ini …is an absolute path. Layers may only be referenced inside data/ or outputs/
Misspells a field as populaton Field 'populaton' does not exist. Available fields: name, road_type, lanes

Validation

Wrong types, missing fields and invented arguments are rejected before QGIS runs.

Sandbox

Inputs resolve only inside data/ and outputs/; results are forced into outputs/ whatever name is proposed.

Self-correction

Errors are written to be read by the model — which is what makes recovery possible in Week 5.

Week 4 · The detail I'm proudest of

“500 metres” on data measured in degrees

QGIS buffers in layer units. Our data is EPSG:4326, where the unit is the degree — so a naïve DISTANCE: 500 means 500 degrees: a buffer larger than the planet.

What the tool does instead

  • Reads the layer's own CRS and longitude
  • Computes the correct UTM zone from it — here EPSG:32640, UTM 40N
  • Reprojects, buffers in true metres, reprojects back

UTM keeps distance accurate to ~0.1% inside its zone. Web Mercator — the usual reflex — would stretch a buffer ~10% at this latitude.

Proved by measurement, not trust

The test buffers by 5 000 m, reprojects the result into UTM, and checks how much the layer actually grew.

0 mmeasured error on a 5 km buffer

The model just says distance_meters: 500. Getting this right once, in tested code, is exactly what the tool layer buys.

A real bug the tests caught

The first convex_hull used QGIS's obvious-looking native:convexhull — which computes a hull per feature. On a 3-point layer it returned 3 degenerate hulls instead of one enclosing polygon. No error; just a quietly wrong answer.

That is the case for the tool layer in miniature. A model writing its own code would have made the same reasonable-looking mistake — and nothing would have caught it.

Limits & next

What is deliberately not done yet

Known limits Honest

  • No multi-step loop. One tool per request — chaining is Week 5.
  • The tool set is fixed. An analysis nobody defined a tool for cannot be performed — the measured cost of function calling over code generation.
  • Vector data only. No raster or terrain analysis.
  • Sample layers are simplified teaching data, labelled as such in the files.

Week 5 — the execution loop

  • Keep calling the model while it wants tools — inspect, act, react, chain
  • Recover from failures using the error messages already written for that purpose
  • Carry conversation memory across steps

Everything the loop needs is in place: validated tools, self-describing errors, and a QGIS instance that stays alive.

Beyond the roadmap

A hybrid path resolves the flexibility limit: strict tools by default, with a sandboxed code-generation escape hatch for the exceptions — safe by default, flexible when needed. And because public benchmarks now exist (GeoAgentBench, GISAgentBench), a later phase can report a score rather than a demonstration.
